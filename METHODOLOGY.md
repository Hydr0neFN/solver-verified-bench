# Methodology, and what this benchmark does not measure

Read this before quoting any number from the results.

## What is being compared

Five model configurations, driven through the Antigravity CLI (`agy`), one prompt per
run, no conversation history:

| id | family |
|---|---|
| `gemini-3.7-flash-high` | Gemini Flash, high reasoning effort |
| `gemini-3.7-flash-medium` | Gemini Flash, medium reasoning effort |
| `gemini-3.6-flash-high` | previous Flash generation |
| `gemini-3.1-pro-high` | Gemini Pro |
| `gpt-oss-120b-medium` | GPT-OSS 120B |

Reasoning effort (`low` / `medium` / `high`) is a separate axis from the model. It is
encoded in the model id here because that is how the CLI exposes it.

## Three tiers

| tier | tasks | trials per cell | why it exists |
|---|---|---|---|
| 1 | 12 reasoning + 3 fact batteries | 2 | baseline. Every model scored 100% on all of it, so it discriminates nothing and is kept only to show where the floor sits. |
| 2 | 14, solver-verified | 3 | written after tier 1 saturated. Every answer produced by a brute-force or DFS solver that also confirmed the answer is unique. |
| 3 | 4 composite grid-induction rules | 5 | built to settle the single task tier 2 disagreed on. |

Task files are generated by `bench/make_tier{1,2,3}.py` from fixed seeds, so the exact
prompts in `tasks/` are reproducible. The generators also emit the answer keys.

## The part that most changes how you should read this

**The models had shell and code-execution access during every run, and used it.**

`agy` gives the model a working directory and a shell. On the grid-induction tasks the
models wrote and ran Python to search for the transformation rule — roughly a hundred
scripts across the runs, with names like `solve14.py`, `test_conv_gf2.py`,
`test_ca_conflict.py`, and one that simply printed the XOR of every example pair.

Consequences, stated plainly:

- These scores measure **model + tools**, not reasoning in isolation. Do not quote them
  as "reasoning ability".
- Every model had the **same** access, so the *comparison between models* stays fair.
- The long latencies on induction tasks are iteration loops, not slow token generation.
- The fact batteries instruct the model not to use any tool. That instruction was **not
  enforced** with `--sandbox`, and compliance was not verified. Treat the fact-axis
  results as an upper bound, and re-run with `agy --sandbox` for a clean measurement.

## Scoring

Mechanical, in `bench/score.py`, driven by the answer keys in `truth/`. The prompt
requires the reply to end with `FINAL: <answer>`; only that line is parsed.

Empty replies are not silently dropped:

| cause | treatment |
|---|---|
| model burned its own time budget and returned nothing | **scored 0** |
| provider-side failure (quota exhausted, auth) | excluded |

Dropping timeouts would flatter whichever model is slowest, which is exactly the
comparison being made.

## Two answer keys were wrong, and were corrected after seeing results

Both were caught by the same rule: *if every model misses an item, suspect the key
before the models.* Both corrections were applied identically to all models, so neither
can favour one. Both are documented inline in `truth/tier2.json`.

1. **Largest exactly-representable integer in IEEE 754 binary64.** The key said
   `2^53`. Every model answered `2^1024 - 2^971`, which is correct; `2^53` answers the
   different question of the largest *n* below which every integer is representable.
2. **The scheduler spec-contradiction item.** It shipped with a redundant answer: the
   requirement "must reassign on lease expiry" contradicts both "executed at most once"
   and "never executed concurrently". 7 of 9 runs gave the stronger of the two pairs.
   The key now accepts either.

A third item was audited and survived. On one composite grid rule all models converged
on the same wrong grid, which usually signals an ambiguous task. `bench/audit_ambiguity.py`
enumerates a 64-rule family and confirms the examples pin the rule uniquely, and that
both parity values are demonstrated for every column the query depends on. The task is
sound; the models simply got it wrong together.

## Limits

- **Small trial counts.** 2–5 per cell. Large gaps are visible, small ones are not. The
  tier-2 induction item is the cautionary example: at 3 trials it pointed the opposite
  way from what 20 trials on four rules showed.
- **Bespoke tasks.** Written for this test, which avoids contamination but makes the
  numbers incomparable to any published leaderboard.
- **Two accounts.** Runs were split across two subscription tiers when quota ran out.
  Accuracy is unaffected — the same model id serves the same weights — but **latency is
  not comparable across that boundary**. See `ACCOUNT-PROVENANCE.md`.
- **One provider, one day.** Nothing here generalises to other work or to the next
  model revision.
