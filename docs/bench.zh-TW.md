# Bench 設定

[回 README](../README.md)

Runner 怎麼掃題、並行度為何會左右結果，以及為什麼有一題 trial 數特別多。這些內容出自 [METHODOLOGY.md](../METHODOLOGY.md)，完整方法請看那份文件。

## Runner

用法是 `bench/run-model.sh <model-slug> [parallelism] [tiers] [budget]`。`budget` 是選填，例如 `15m`，用來覆蓋每層的 print timeout。預設 tier 1 給六分鐘（`6m`，以耗時秒數計算是 420），Tier 2、Tier 3 各給十分鐘（`10m`、700）。只要格子裡已有非空輸出就跳過，所以配額卡住之後可以放心重跑。預設並行度是 6。底下呼叫的是 `agy -p <prompt> --model <slug> --output-format text`。

## 並行度會改變結果，所以它算方法的一部分

Runner 有一個並行度參數。這不是方便用的旋鈕——設錯了，你量到的是 harness，模型反而沒量到。

同時跑三個 Tier 3 格子、預算十分鐘時，有個模型每次都固定卡在 **~201 秒**失敗，回覆是空的，stderr 也沒有東西。改成單獨跑、預算十五分鐘，同一題 **3 分 14 秒**就答對收工。模型本身沒變；是並行時被節流了，照那樣計分就會把它能解的題記成「解不出來」。（那個模型後來因為別的原因沒放進這些表——它一直沒跑夠覆蓋率可以報——但這個教訓不隨它消失。）

判斷的線索是失敗花多久，計分器也用這個：

| 失敗前耗時 | 判讀 | 處理 |
|---|---|---|
| 幾秒 | 配額或容量拒絕 | 排除，與模型無關 |
| 並行下約 200 秒 | 被節流 | 排除，改單獨重跑 |
| 整個預算（約 600 秒以上） | 模型沒有收斂 | 計 0 |

Gemini 系列扛得住六路並行，別的模型不一定。要加新模型，先單獨跑、預算給寬一點，每次失敗都先看耗時再決定信不信。

## 有一題 trial 數比別人多的原因

`H1_arc2` 的 trial 數比其他格子都多：`gemini-3.6-flash-high` 九次、`gemini-3.7-flash-high` 八次，其他格子都是三次。這是刻意安排的。那兩個模型分歧最大的就是這一題，三次 trial 分不出是真差距還是運氣好——這份測試在歸納層已經吃過一次虧：原本 2 比 3 的領先，跑到二十次 trial 時完全翻過來。

兩個模型加的次數一樣；3.7 少一次，只因那一對跑到一半中斷。加測之後差距變大、沒有縮小，所以才把它當成一個結果來寫，不當成雜訊。其他模型都沒加 trial，所以 `H1_arc2` 那列只代表它抽得比較多，不能拿來跟隔壁比樣本數。
